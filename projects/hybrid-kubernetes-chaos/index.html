Hybrid Kubernetes Chaos Lab

A physical Kubernetes environment connected to Azure through Arc and managed through Flux GitOps, built to turn resilience claims into measured runtime evidence. The lab runs kubeadm Kubernetes on Ubuntu Server with containerd and Calico, then deliberately injects pod, CPU, and network faults while an in-cluster probe measures service behavior.

REQUIREMENTS & CONSTRAINTS

Build a real hybrid environment without turning the lab into a recurring cloud bill.

The lab was intentionally built on a physical Lenovo P620 with 32 GB of DDR4 and Ubuntu Server. It runs headless and is administered remotely, keeping the hardware useful as a persistent on-premises-style Kubernetes target without requiring paid managed-cluster compute.

The design goal is not simply to show a green Kubernetes dashboard. The cluster must be remotely manageable through Azure, reconcile desired state from Git, and generate repeatable evidence for how workloads behave when individual components are deliberately degraded or removed.

GITOPS & OPERATIONS

The cluster is operated through desired state, not one-off deployment commands.

Azure Arc-enabled Kubernetes

The physical cluster is registered in Azure as k8s-edge-01, providing a cloud control-plane view and remote Cluster Connect path without moving the workload into AKS.

Flux reconciliation

Flux watches the portfolio repository and applies the workload manifests under projects/hybrid-kubernetes-chaos/gitops. A Git change from two to three replicas reconciled automatically without a manual kubectl apply.

Three-replica service baseline

The hybrid-demo NGINX workload runs three replicas behind a ClusterIP Service with readiness/liveness probes and explicit CPU/memory requests and limits.

Remote management boundary

Azure Arc Cluster Connect is demonstrated as a remote administration path. The proxy session is intentionally treated as a management dependency, not as the application data path used for availability measurement.

MEASURED CHAOS RESULTS

Three different failure modes, measured at runtime.

Each experiment pairs a bounded fault with independent service measurements so the portfolio distinguishes observed behavior from design assumptions.

01 · POD FAILURESelf-healing in 6.89 seconds

One replica was deleted from a healthy 3/3 Deployment. Capacity dropped to 2/3, Kubernetes created a replacement, and the Deployment returned to 3/3 Ready and Available in 6.89 seconds. The in-cluster probe recorded 109/109 successful requests: 100% observed availability.

02 · CPU SATURATION30.73 seconds under the 250m CPU limit

One running replica was deliberately CPU-saturated for 30.73 seconds. The pod remained Running and Ready with zero restarts, while the Service completed 110/110 probe requests successfully: 100% observed availability.

03 · NETWORK ISOLATIONEndpoint unreachable; Service still available

An independent probe verified the selected pod IP as reachable before the policy, unreachable during the 30-second deny-ingress NetworkPolicy, and reachable again after cleanup. The pod still reported Ready=True with zero restarts, while the Service completed 100/100 requests successfully.

MEASUREMENT METHOD

The test harness was corrected when the first metric measured the wrong thing.

In-cluster availability probe

A temporary curl pod calls http://hybrid-demo.hybrid-lab.svc.cluster.local through normal Kubernetes DNS and Service routing. This measures the application Service path rather than the management workstation.

Discarded port-forward artifact

An early test reported 56.82% availability because kubectl port-forward service/... was tied to a backend pod that was deleted. That result was rejected because it measured tunnel survivability, not Kubernetes Service availability.

Direct network assertion

The network experiment creates a separate curl pod and verifies the target pod IP directly: HTTP 200 before isolation, timeout/HTTP 000 during isolation, and HTTP 200 after cleanup.

Bounded fault injection

CPU and network experiments use explicit time limits and cleanup paths. The scripts write timestamped local evidence so each result can be tied to a specific run rather than a screenshot-only claim.

KNOWN LIMITATIONS

The strongest current limitation is physical, not Kubernetes-specific.

Single-node cluster

All application replicas currently run on k8s-edge-01. The lab therefore proves pod-level self-healing and Service continuity, but a physical node failure would remove every replica. Node-level resilience requires at least one additional worker.

Readiness is not end-to-end reachability

During the NetworkPolicy experiment the target pod stayed Ready even though an independent workload could not reach its pod IP. That is useful evidence that local health checks alone do not represent every client network path.

Arc proxy is a management session

Cluster Connect uses a temporary localhost proxy. If that process stops, remote kubectl commands fail until the proxy is restarted; this does not indicate that the Kubernetes workload itself is unhealthy.

Next resilience tier

Node-failure testing should wait for another physical worker. After that, a dedicated chaos platform can add richer scheduling and fault types without replacing the simple scripts that establish the baseline.
