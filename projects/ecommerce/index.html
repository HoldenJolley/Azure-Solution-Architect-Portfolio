ARCHITECTURE PROBLEM

Keep checkout responsive without losing control of inventory.

The design separates synchronous customer-facing API work from asynchronous fulfillment. Front Door provides a global edge and WAF boundary, regional App Service instances host the API and background workers, Cosmos DB holds commerce state, and Service Bus decouples inventory, payment, shipping, and analytics processing.

KEY DECISIONS

Complexity is introduced only where the requirement earns it.

App Service instead of AKS

The workload needs independently deployable API and worker processes, not a Kubernetes control plane. App Service keeps the operational surface smaller while preserving scale and managed identity.

Service Bus for asynchronous commerce work

Payment, shipping, inventory, and analytics can fail or retry independently without making the customer request wait for every downstream dependency.

Cosmos DB with a clear inventory authority

The design prioritizes a defined inventory-consistency boundary rather than enabling multi-master writes everywhere and creating ambiguous stock ownership.

Private networking for production-oriented data services

Private endpoints and DNS keep data-plane services off unnecessary public paths while managed identities remove application secrets from service-to-service authentication.

Cloud validated
Compiler and live Azure control-plane validation are complete for the dev architecture.

GitHub Actions lints and builds the Bicep template and all dev, test, and production parameter files, then authenticates to Azure through secretless OIDC and runs a subscription-scope Resource Manager What-If. The deployment job remains gated and has not been run.

Project scope: this repository contains the architecture, Infrastructure as Code, contracts, deployment tooling, ADRs, testing guidance, and operational documentation. It is a reference architecture package; a complete production commerce application implementation is intentionally outside the current scope.
