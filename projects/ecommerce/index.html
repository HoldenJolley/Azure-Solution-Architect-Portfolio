REQUIREMENTS & CONSTRAINTS

Keep checkout responsive without making consistency vague.

The customer-facing API should acknowledge work quickly while downstream inventory, payment, shipping, and analytics can proceed independently. The design therefore keeps the synchronous path small, makes inventory reservation an explicit consistency boundary, and pushes long-running work into asynchronous consumers.

The reference must also be reproducible from source control, use managed identity by default, keep data-plane services on private paths where practical, and demonstrate regional resilience without pretending every stateful dependency is automatically active-active.

ARCHITECTURE CONSTRAINTS

Requirements decide where complexity belongs.

No Kubernetes by defaultRegional HTTP APIs and workers need managed compute, not necessarily a Kubernetes control plane. App Service reduces platform overhead while retaining identity, VNet integration, health checks, slots, and scale options.
Async after acceptanceInventory, payment, shipping, and analytics work is decoupled through Service Bus where the business flow does not require the customer request to wait.
Separate operational and analytical pathsCosmos DB holds commerce state while business events can be projected into Data Lake without placing analytics on the checkout critical path.
Dependency-specific resilienceFront Door, App Service, Cosmos DB, and Service Bus have different recovery characteristics; RTO and RPO cannot be reduced to one generic “multi-region” claim.

COMPONENT RESPONSIBILITIES

The architecture makes ownership explicit.

API

Owns product, cart, checkout acceptance, and order retrieval. It stays focused on the customer-facing request path rather than performing every downstream side effect inline.

Inventory worker

Owns reservation, release, and commit transitions. Reservation is the deliberate consistency boundary used to prevent ambiguous stock ownership.

Payment worker

Owns payment-provider interaction and requires idempotent behavior so retries do not duplicate external side effects.

Shipping worker

Handles fulfillment transitions independently from the checkout request so shipping failures do not force the customer-facing API to remain open.

Analytics worker

Copies business events into Data Lake. Analytics can lag or recover independently because it is intentionally outside the checkout critical path.

Platform services

Cosmos DB holds operational state, Service Bus carries asynchronous work, Key Vault protects secrets/keys, and Application Insights + Log Analytics provide the operational evidence needed to diagnose failures.

REGIONAL DESIGN

Multi-region compute does not magically make every dependency multi-region.

The production reference places API/worker compute in two regions behind Front Door. Cosmos DB is modeled across both regions with one authoritative write region and automatic failover. Front Door can route around an unhealthy API origin and Cosmos can promote the configured secondary region.

Service Bus continuity is intentionally treated as a separate architecture problem. A regional Service Bus outage can pause asynchronous work in the current baseline, so the project does not claim a messaging RTO that has not been designed and tested.

FAILURE BEHAVIOR

Design for what breaks, not only for the happy path.

Primary API origin unhealthy

Front Door routes to the healthy secondary origin in the production reference profile.

Worker crashes mid-message

The locked message becomes available for redelivery. Consumers must be idempotent because the crash may happen after an external side effect but before message completion.

Poison message

Retries stop at the configured limit and the message moves to the dead-letter queue for operational handling rather than retrying forever.

Payment provider unavailable

Retry/backoff applies, the order remains incomplete, and reserved inventory must eventually be released instead of becoming permanently stranded.

Cosmos write region unavailable

Cosmos failover promotes the configured secondary region. Observed recovery still needs to be validated under a deployed test.

Service Bus regional outage

Asynchronous processing can pause. The current reference records that limitation instead of hiding it behind a generic multi-region label.

POST-DEPLOYMENT RESILIENCE TESTS

What I would prove at runtime.

01Traffic and regional failover

Make the primary API origin unhealthy and verify Front Door moves traffic. Exercise controlled Cosmos regional failover and record observed recovery instead of assuming the service behavior meets the target.

02Message integrity

Crash a worker after a side effect but before completion, prove idempotent redelivery, inject a poison event, and verify dead-letter handling and the associated runbook.

03Business consistency

Simulate payment timeouts and verify inventory release, then run a high-contention inventory race to prove the reservation boundary prevents overselling.

KEY DECISIONS

Complexity is introduced only where the requirement earns it.

App Service instead of AKS

The workload needs independently deployable API and worker processes, not a Kubernetes control plane. App Service keeps the operational surface smaller while preserving scale, managed identity, VNet integration, health checks, and deployment slots.

Service Bus for asynchronous commerce work

Payment, shipping, inventory, and analytics can fail or retry independently without forcing the customer request to wait for every downstream dependency.

Cosmos DB with a clear inventory authority

The design prioritizes a defined inventory-consistency boundary rather than enabling multi-master writes everywhere and creating ambiguous stock ownership.

Private networking for data services

Private endpoints and DNS keep data-plane services off unnecessary public paths while managed identities remove application secrets from service-to-service authentication.
